# Existing agent memory systems: source architecture and implications for oxibrain

Date: 2026-10-23 (Asia/Seoul). Status: research and proposed follow-up; this report adopts no implementation or architecture change.

The strongest lesson from current implementations is to treat stored evidence, synthesized knowledge, working context, and the final model input as separate objects. A vector store or a temporal graph covers only part of that path. For oxibrain, the immediate priority remains the proposed [M12 reliable-recall work](../spec/reliable-recall-v1.md). The useful additions are explicit retrieval-channel coverage, summary-to-source expansion, and lifecycle checks for background work. Replacing the immutable ledger with another system's mutable memory representation would give up existing guarantees without a demonstrated benefit.

## Scope and evidence

This study follows six systems through their public source: Mem0 OSS, current Letta Code, Graphiti, Hindsight, LangMem, and Mastra Observational Memory. They cover a memory SDK, a stateful agent runtime, a temporal graph, a retrieval-and-reflection engine, workflow primitives, and continuous context compression. They are representative choices, not an exhaustive inventory or a product ranking.

- Source snapshots are pinned below. Fifty-two selected source/documentation files were downloaded and their Git blob hashes verified. Entry points and the specific regions linked in this report were inspected; this was not a full audit of all fifty-two files or their repositories.
- Official live documentation was checked alongside source. The old Letta repository's redirect README was also read. Mem0 Platform and Zep service architecture is described only to the extent documented by their maintainers; their hosted implementations were not inspected.
- Four isolated probes executed two reviewed pure functions from the pinned files. No third-party package was installed or imported wholesale. No complete SDK, database service, agent harness, LLM extraction, or provider benchmark was run.
- The snapshots track default-branch source, which can be newer than published packages. A GitHub “latest release” in a monorepo can refer to a different package; it is not evidence that a particular installed SDK contains this code.
- External benchmark scores, latency claims, and model-quality claims were not reproduced and are not used to rank the systems. The earlier [paper and oxibrain investigation](2026-10-23-recall-quality-and-evidence.md) remains a separate source of evidence.

## The structures being compared

These are simplified flows of the inspected paths, rather than claims that each product has only one mode:

```text
Mem0:     messages -> additive extraction -> memory/entity collections + SQL history
          query -> dense candidates + keyword/entity scoring -> memory results
Letta:    agent / background worker -> memory Git commits -> core-memory compiler
          deferred files / transcript search -> additional context on demand
Graphiti: episodes -> entity/edge resolution + temporal invalidation -> context graph
          full-text / dense / graph traversal -> configured reranking -> graph results
Hindsight:content -> source chunks + extracted facts/links -> background observations
          multi-arm recall -> fusion/reranking/budgets; reflect -> iterative evidence use
LangMem:  agent tools / background runnable -> namespaced BaseStore items
          store search -> application-selected prompt context
Mastra:   persisted messages -> Observer buffers -> active observations -> Reflector generations
          observations + unobserved messages -> actor; optional recall -> source history
```

The products place different responsibilities at the memory boundary. Mem0 and Graphiti mainly return retrieved objects. LangMem supplies composable primitives. Letta and Mastra own more of the agent's context lifecycle. Hindsight offers both retrieval and a separate model-driven reflection operation. Comparing their answer scores without matching these responsibilities would confound memory with orchestration and answer generation.

## 1. Mem0: current additive extraction, with a dense-gated scoring pool

The current Python OSS path is substantially different from the familiar older description of an LLM selecting `ADD`, `UPDATE`, `DELETE`, or `NONE` and optionally maintaining an external graph. The official [migration guide](https://docs.mem0.ai/migration/oss-v2-to-v3) describes automatic ADD-only extraction and removal of graph memory from OSS. Manual update/delete APIs still exist. ADD-only automatic extraction therefore does not make the whole store an immutable ledger.

**Write path.** `add()` collects the latest ten scoped messages and ten semantically retrieved existing memories, then makes one additive-extraction call. Extracted texts are embedded, content-hash duplicates are skipped against the retrieved set and current batch, and accepted memories receive random UUIDs. The vector-store insert is followed by SQL change history, entity linking, and message persistence. The history/entity steps have their own fallback/error handling; this is a multi-store sequence, rather than one ledger transaction explaining all derived state. [Extraction and persistence](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/memory/main.py#L881), [manual update](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/memory/main.py#L1829).

**Stored representation.** Memory payloads contain text, hash, scope identifiers, timestamps, optional attribution, and metadata. A parallel entity collection links entity representations to memory IDs. This entity collection is not the removed external graph integration. The default configuration also names a separate SQLite history database. [Configuration](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/configs/base.py#L29), [entity collection](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/memory/main.py#L1100).

**Read path.** `_search_vector_store()` overfetches dense results, separately obtains keyword scores and entity boosts, then constructs its candidate list exclusively from the dense results. `score_and_rank()` first applies the semantic threshold, then combines the surviving candidates' scores. A keyword-only hit cannot enter this list through its keyword score. A low-dense-score hit is excluded before a strong keyword/entity boost can help. Optional reranking operates later. These are properties of this inspected Python path, not a claim about the hosted service or every backend's internal behavior. [Candidate construction](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/memory/main.py#L1642), [scoring](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/utils/scoring.py#L60).

**Implication for oxibrain.** Inspect candidate eligibility before tuning fusion weights. M12 should prove that an exact lexical-only source can survive independently of dense recall. Content-level duplicate suppression can help ranking, but must never replace oxibrain's source-occurrence episode identity. A mutable text update is not a substitute for a declaration episode and deterministic fold. Mem0 Platform's graph and temporal features require a separate service-level assessment; the OSS source does not establish their implementation.

## 2. Letta: committed memory files compiled into a stateful agent

The current [`letta-ai/letta` README](https://github.com/letta-ai/letta/blob/8816d3a8516893bfdc0fa14bfb1235226012e295/README.md) directs development to `letta-code`; the retired V1 API server remains on `archive`. Consequently, the older core/archival/recall-memory account is historical context, not a sufficient account of the present local runtime.

**Write path.** Current [memory documentation](https://docs.letta.com/configuration/memory) describes editable Git-backed MemFS and background dreaming. In source, the memory worker edits a private worktree, integrates completed commits, retains a conflicting branch for diagnosis, and refreshes the compiled prompt after integration/sync. Cancellation and merge outcomes are explicit. This is an agent-memory authoring workflow with concurrency handling, rather than passive ingestion into a search database. [Worker integration](https://github.com/letta-ai/letta-code/blob/6c8b08fedfb6f3fb437163ede8320a387151693f/src/agent/subagents/memory-worker.ts#L66).

**Read path.** The local compiler obtains Git `HEAD`, enumerates committed Markdown paths with `ls-tree`, and reads selected bodies through `git show HEAD:path`. In MemFS v2, core files and the root memory index are embedded; child memory indexes can appear as deferred directory pointers. The compiled result carries the memory revision and raw-system-prompt hash. This gives a concrete identity to the memory snapshot used for compilation. It does not mean every file in the memory repository is automatically placed in the prompt. [Committed input collection](https://github.com/letta-ai/letta-code/blob/6c8b08fedfb6f3fb437163ede8320a387151693f/src/backend/local/system-prompt-compilation.ts#L65), [root/deferred rendering](https://github.com/letta-ai/letta-code/blob/6c8b08fedfb6f3fb437163ede8320a387151693f/src/backend/local/system-prompt-compilation.ts#L154), [compilation receipt](https://github.com/letta-ai/letta-code/blob/6c8b08fedfb6f3fb437163ede8320a387151693f/src/backend/local/system-prompt-compilation.ts#L435).

**Other state.** The local store persists conversation records and message transcripts separately. Local transcript search scans stored conversations and ranks text matches; it explicitly rejects `vector` and `hybrid` search modes. It also demotes the current question/search echoes on unscoped recall. Thus current local Letta should not be described as automatically running a vector search over all prior conversations. [Transcript search](https://github.com/letta-ai/letta-code/blob/6c8b08fedfb6f3fb437163ede8320a387151693f/src/backend/local/transcript-search.ts#L517), [local persistence](https://github.com/letta-ai/letta-code/blob/6c8b08fedfb6f3fb437163ede8320a387151693f/src/backend/local/local-store.ts#L2844).

**Implication for oxibrain.** A small stable context plus inspectable pointers is useful, as are revision receipts and background-write conflict handling. Git history, however, serves a different contract from oxibrain's deterministic assertion projection. Copying agent-owned memory-file editing would cross oxibrain's Full Reader and no-authoring boundary. Keep the reusable mechanism at the context/projection layer: bounded profile material, evidence pointers, explicit revisions, and source expansion through existing operations.

## 3. Graphiti: episode provenance and temporal relationship maintenance

**Write path.** `add_episode()` retrieves previous episodes for context, creates or loads an episode, extracts/resolves entities and relationships, resolves duplicate/contradictory edges, hydrates attributes, and saves graph objects. Communities can be updated separately. Extracted relationships retain episode IDs. Their fields distinguish `created_at`/`expired_at` from `valid_at`/`invalid_at`, with an additional reference time. [Ingestion](https://github.com/getzep/graphiti/blob/afea04fecd34671c6608fd2a877c5372ff55ee29/graphiti_core/graphiti.py#L1430), [relationship model](https://github.com/getzep/graphiti/blob/afea04fecd34671c6608fd2a877c5372ff55ee29/graphiti_core/edges.py#L263).

Contradiction resolution is not just a date comparison. The resolver selects duplicate/invalidation candidates with model-assisted decisions, then temporal routines update validity and expiration fields. The inspected edge model creates random UUIDs by default. Raw episode retention is configurable and can be disabled before saving. These mechanisms do not establish an oxibrain-style immutable-ledger or byte-identical-rebuild guarantee. [Resolution orchestration](https://github.com/getzep/graphiti/blob/afea04fecd34671c6608fd2a877c5372ff55ee29/graphiti_core/utils/maintenance/edge_operations.py#L591), [temporal updates](https://github.com/getzep/graphiti/blob/afea04fecd34671c6608fd2a877c5372ff55ee29/graphiti_core/utils/maintenance/edge_operations.py#L715), [raw-content option](https://github.com/getzep/graphiti/blob/afea04fecd34671c6608fd2a877c5372ff55ee29/graphiti_core/graphiti.py#L1031).

**Read path.** Configured full-text, vector, and breadth-first graph searches produce separate result lists using shared search filters and group scope. Recipes select fusion/reranking policies such as RRF, MMR, node distance, or cross-encoder mode. The latter is a configurable interface: the default client instantiated by `Graphiti` is `OpenAIRerankerClient`; the name alone must not be interpreted as proof of a local neural cross-encoder. The RRF recipe does not use that reranking path. [Search channels](https://github.com/getzep/graphiti/blob/afea04fecd34671c6608fd2a877c5372ff55ee29/graphiti_core/search/search.py#L289), [reranking](https://github.com/getzep/graphiti/blob/afea04fecd34671c6608fd2a877c5372ff55ee29/graphiti_core/search/search.py#L373), [default clients](https://github.com/getzep/graphiti/blob/afea04fecd34671c6608fd2a877c5372ff55ee29/graphiti_core/graphiti.py#L340).

**Deployment boundary.** Graphiti supplies a graph framework, with graph database and model dependencies supplied by the application. [Zep's official overview](https://help.getzep.com/graphiti/getting-started/overview) describes a managed Context Lake on Konig using Graphiti-derived temporal artifacts. Graphiti source is not a source audit of Zep's complete ingestion, governance, or context service.

**Implication for oxibrain.** Separate valid time from acquisition/transaction time throughout public reads; retain the source episode for each claim. Four timestamp fields alone do not verify historical names, merges, or complete competing-assertion reconstruction. M12's common `ReadScope` and historical fold remain necessary. Borrow retrieval-channel and tracing patterns without adding a graph database or delegating truth resolution to a retrieval adapter.

## 4. Hindsight: source-linked consolidation, multi-arm recall, and separate reflection

**Storage and retain.** The default memories extension uses Postgres rows in `memory_units`, links in `memory_links`/`unit_entities`, and SQL retrieval; the current source also supports a memories-store extension boundary. Retention extracts facts and chunks, augments embedding input with dates, generates embeddings, and persists fact/source relationships. Current retain documentation distinguishes `world` from the bank agent's own `experience`; background consolidation adds `observation` units. It would be inaccurate to carry an older four-type description including `opinion` into this inspected retain path. [Default store](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-api-slim/hindsight_api/engine/memories/__init__.py#L1), [extraction/embedding](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-api-slim/hindsight_api/engine/retain/orchestrator.py#L1354), [fact types](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-docs/docs/developer/retain.md#L53).

**Consolidation.** The background consolidator creates or revises observations from raw facts. Observations track supporting memory IDs and proof counts. User-defined mental models are a separate, query-driven abstraction refreshed through reflection. The delta-retain path explicitly removes observations supported by outgoing source facts when replacing chunks. Source lifecycle therefore reaches synthesized memory, rather than stopping at a citation string. This is a useful implementation pattern; a proof count is still not a calibrated confidence or oxibrain's formal uncertainty. [Consolidation model](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-api-slim/hindsight_api/engine/consolidation/consolidator.py#L1), [replacement propagation](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-api-slim/hindsight_api/engine/retain/orchestrator.py#L1253).

**Recall.** The common interface exposes dense, keyword, graph, and temporal arms. The default SQL path can combine dense/keyword retrieval, after which fusion, candidate trimming, payload hydration, reranking, scoring, and budget selection follow. RRF is the normal fusion path; interleave is available for consolidation deduplication, where preserving a strong single-channel hit can matter more than agreement across channels. This demonstrates why a query's purpose can require a different ranking policy. [Retrieval interface](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-api-slim/hindsight_api/engine/search/retrieval.py#L129), [fusion policies](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-api-slim/hindsight_api/engine/search/fusion.py#L112), [wired reranking path](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-api-slim/hindsight_api/engine/memory_engine.py#L10403).

Several public-field meanings matter when comparing this with M12:

- `temporal_window` influences a retrieval arm; it is not a hard exclusion of every result outside that time window. The `created_after`/`created_before` arguments are documented in the source as change windows over `updated_at`, rather than a historical snapshot contract.
- `max_tokens` counts fact text. Chunks, entities, and source facts have separate budgets; it is not a single bound on the complete serialized response or rendered model context.
- Fact selection skips an oversized fact and considers later ones. If a positive budget cannot fit any fact, it deliberately returns the first fact whole, over budget.
- The shared counter uses a configured encoding, defaulting to `o200k_base`. Counting exactly under that encoding does not by itself prove a match to every consuming model's tokenizer.

These are documented choices, not independently reproduced end-to-end defects. [Recall contract](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-api-slim/hindsight_api/engine/memory_engine.py#L9252), [budget selector](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-api-slim/hindsight_api/engine/fact_budget.py#L43), [token encoding](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-api-slim/hindsight_api/engine/token_encoding.py#L31).

**Reflect.** A separate model-driven loop can search/read mental models, search observations, recall raw facts, and expand evidence before synthesizing a response. The available callbacks and iteration/context budgets are explicit; the actual sequence is agent-driven, rather than a mandatory fixed pass through every tier. Retrieval and answer synthesis should therefore be evaluated separately. [Reflect loop](https://github.com/vectorize-io/hindsight/blob/35451e5fa5b828d90593561bc9fb2d5deb242a32/hindsight-api-slim/hindsight_api/engine/reflect/agent.py#L617).

**Implication for oxibrain.** Make synthesized items inspectable through their live support, and carry deletion/redaction/revision changes through dependent summaries. Keep recall a bounded evidence operation. A future iterative synthesis mode belongs in a separately measured orchestration layer using existing engine operations; it is not a reason to add MCP tools beyond the cap. Adopt skip-and-continue packing, while retaining M12's strict requested-context budget and explicit tokenizer quality instead of Hindsight's over-budget floor.

## 5. LangMem: memory policies composed over an application-owned store

**Write path.** LangMem separates functional memory extraction from persistence. `MemoryManager` uses schema-constrained extraction/update/removal over supplied existing items. `MemoryStoreManager` first searches the configured namespace, enriches the retrieved items, optionally runs further phases, and applies resulting puts/deletes through `BaseStore`. Agent-facing management tools also call namespaced store put/delete directly. The application chooses schemas, permissions, storage, and invocation points. This is a workflow toolkit, rather than a universal memory database with a fixed truth model. [Manager extraction](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/knowledge/extraction.py#L237), [search/enrich/persist](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/knowledge/extraction.py#L1006), [management tool](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/knowledge/tools.py#L271).

**Read and context.** The search tool delegates query, filter, limit, and offset to `BaseStore`. Namespace templates provide an organization/user/agent partitioning mechanism; an application must still bind those values to its authenticated scope. The library does not turn that mechanism into oxibrain's ledger-derived trust policy. Prompt composition and the complete model-input budget remain the application's responsibility. The README distinguishes ephemeral `InMemoryStore` from persistent database-backed stores. [Search tool](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/knowledge/tools.py#L456), [storage boundary](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/README.md).

**Background path.** `LocalReflectionExecutor` queues work with an optional delay and cancels a pending task for the same thread when another is submitted. Its local queue and worker are process-resident; persistent memories do not imply durable queued work. A remote executor is a different deployment path. The short-term summarizer separately tracks summarized message IDs and a last-summary cursor. [Local queue/debounce](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/reflection.py#L273), [queue execution](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/reflection.py#L401), [summary coverage state](https://github.com/langchain-ai/langmem/blob/48e3c11f5bb527282c7d5339c6a87a0b35abccfc/src/langmem/short_term/summarization.py#L53).

**Implication for oxibrain.** Separate capture timing from consolidation timing, and make schema/policy composition explicit. For oxibrain, background decisions must produce ledger-explained artifacts and survive restart through existing durable job state. Reusing an in-process debounce queue would not satisfy that contract. Avoid treating framework namespace isolation, extraction schemas, and historical truth reconstruction as interchangeable features.

## 6. Mastra: continuous observation, generation-based reflection, and optional retrieval

**Write and activation path.** Observational Memory persists raw messages and runs an Observer as thresholds are reached or buffered work is prepared. A turn activates stored observation chunks, checks reflection, builds context, and removes the corresponding observed messages from the actor's message list. The important transition is from raw-visible messages to committed observation coverage; it is not deletion of the underlying conversation record. [Turn preparation](https://github.com/mastra-ai/mastra/blob/74761d4c2e46c2f526bf4fe1217e510cac73bd42/packages/memory/src/processors/observational-memory/observation-turn/step.ts#L60).

**Reflection and context.** A Reflector condenses observations into a new generation. The source commits through an OM commit queue, calls the storage generation operation, and verifies that the intended reflection was actually applied before committing side effects. Context building reads active observations, adds temporal annotations, and can inject current-task/continuation fields separately. These are context-lifecycle mechanisms, not just another vector index. The inspected caller is evidence of stale-result handling; cross-process correctness still depends on the storage adapter and was not tested here. [Generation commit](https://github.com/mastra-ai/mastra/blob/74761d4c2e46c2f526bf4fe1217e510cac73bd42/packages/memory/src/processors/observational-memory/reflector-runner.ts#L1482), [context assembly](https://github.com/mastra-ai/mastra/blob/74761d4c2e46c2f526bf4fe1217e510cac73bd42/packages/memory/src/processors/observational-memory/observational-memory.ts#L2081).

**Current source is more than the original compression-only account.** Retrieval mode can preserve observation-group pointers to raw messages, register recall, and optionally index observation groups in a vector store. It is off by default in the inspected type contract. The constructor defaults observation scope to the thread. Resource-scoped observations are deprecated in the type comments in favor of cross-thread retrieval and resource working memory. This demonstrates a separation between ongoing conversation compression and shared durable knowledge. [Retrieval options](https://github.com/mastra-ai/mastra/blob/74761d4c2e46c2f526bf4fe1217e510cac73bd42/packages/memory/src/processors/observational-memory/types.ts#L1039), [scope guidance](https://github.com/mastra-ai/mastra/blob/74761d4c2e46c2f526bf4fe1217e510cac73bd42/packages/memory/src/processors/observational-memory/types.ts#L1121), [resolved configuration](https://github.com/mastra-ai/mastra/blob/74761d4c2e46c2f526bf4fe1217e510cac73bd42/packages/memory/src/processors/observational-memory/observational-memory.ts#L612).

**Budget semantics.** The text counter calls `tokenx.estimateTokenCount`; message framing also uses fixed average overheads. These are thresholding estimates, not proof of an exact consuming-model token bound. Compression thresholds and final-context budget contracts must be distinguished. The repository's architecture discussion also mixes known problems and proposed work; its concurrency discussion was treated as design evidence and checked against the current caller code, rather than copied as a current defect list. [Counter](https://github.com/mastra-ai/mastra/blob/74761d4c2e46c2f526bf4fe1217e510cac73bd42/packages/memory/src/processors/observational-memory/token-counter.ts#L1228).

**Implication for oxibrain.** Keep a summary's source coverage, generation, and pending work visible. Background inference may finish after source edits or redaction; validate its support/revision again before exposing the result. Treat current task state as a small separate context item, rather than stuffing all conversations into a global summary. Retain P10 uncertainty and source links, and keep derived episodes terminal: a projection of prior summaries must not become fresh independent evidence.

## Four isolated function checks

These checks use the pinned `score_and_rank` and `select_facts_within_budget` functions, extracted from reviewed AST function definitions with minimal supplied globals. They do not execute module imports or invoke a complete product. The budget counter returns synthetic fixed units, not real model tokens.

| Probe | Inputs | Observed result |
|---|---|---|
| Mem0 lexical-only eligibility | Dense pool contains A; keyword scores contain only B | A can be returned; B is not introduced into the pool. |
| Mem0 semantic floor | Dense score 0.05, keyword 1.0, entity boost 0.5, threshold 0.1 | Candidate is dropped before additive scoring. |
| Hindsight positive-budget floor | One fact costs 120 counted units; budget is 10 | Fact returned whole; cost 120, `truncated=true` internally. |
| Hindsight skip-and-continue | First fact costs 120; second costs 3; budget is 10 | Second fact returned; cost 3. |

All four assertions passed. The first two establish the scoring helper's behavior, consistent with the inspected Python call site; they do not characterize every vector adapter. The last two establish explicit selector policy, not real tokenizer accuracy or total response size. ## Recommended consequences for oxibrain

These are research recommendations, not newly approved requirements or implemented behavior. The existing [M12 spec](../spec/reliable-recall-v1.md) and [proposed ADR-019](../adr/ADR-019-read-scope-and-evidence-recall.md) were not changed by this study.

| Recommendation | Evidence motivating it | Placement |
|---|---|---|
| Make each retrieval channel's candidate eligibility visible; test a lexical-only correct result and a strong single-channel result. | Mem0's dense candidate gate; Graphiti's separate lists; Hindsight's purpose-specific fusion. | Add explicit cases when implementing M12 B/D; preserve P11 rather than copying a language-specific preprocessing stack. |
| Preserve a route from summary to the exact live source units, plus their coverage and revisions. | Hindsight support dependencies; Mastra observation-group/raw-message pointers; Letta deferred files. | M12 source units and evidence coordinates first; later bounded expansion experiments through existing operations. |
| Separate small stable profile/current task material from query evidence and bulk history. | Letta core/deferred compilation; Mastra thread observations, task fields, and cross-thread retrieval. | Stay within M12's bounded profile/recency design; measure a separate task-state layer before adding one. |
| State which tokenizer and which rendered bytes a budget covers; never silently overrun a strict request. | Hindsight per-component budgets and explicit floor; Mastra estimated threshold counts. | M12 C's canonical rendering, exact/estimate capability, labels/citations, and skip-and-continue behavior. |
| Revalidate background outputs against live source revisions/access state before publication. | Letta worktree integration; Mastra applied-generation check; Hindsight dependent-observation invalidation. | M12 exposure/revision checks for reads; a separate consolidation lifecycle milestone for background writers. |
| Keep assertions and uncertainty separate from retrieval scores, proof counts, and model-produced prose. | Different meanings of Mem0 scores, Graphiti fact resolution, Hindsight proof counts, and compressed observations. | Preserve P1/P2/P4/P10; never use these signals as an authoritative trust tier. |

The first implementation sequence remains: public scope and plane correctness; complete source indexing; source-sized evidence and strict packing; held-out evaluation. Richer consolidation, iterative reflection, and learned ranking follow only once the evidence path is measured. This source study strengthens that sequence; it does not establish a performance gain from the proposed design.

### Concrete additions to the implementation acceptance set

1. A correct exact-identifier document/session result is absent from dense top-k but present in lexical retrieval. It still reaches the eligible candidate union and can be packed.
2. A useful source appears only in one retrieval channel. Fusion and global candidate caps record whether it was retained or discarded; agreement across channels is not treated as independent source corroboration.
3. An oversized first candidate is followed by a short relevant one. The short item survives, while strict rendered-context cost never exceeds the requested budget.
4. The highest-ranked source is larger than the whole budget. Return an allowed source slice/variant or an explicit omission; do not copy an implicit over-budget floor.
5. A summarized source is revised, redacted, or loses visibility while background synthesis runs. The stale result is rejected or recomputed, and its source pointers cannot expose removed content.
6. A summary already covers a raw source. Avoid redundant prompt bytes while retaining the raw occurrence and all independent supporting occurrences in the ledger.
7. Interruption occurs between source persistence, projection/index work, and summary publication. Resume without a missing source, duplicate durable event, or unexplained projection row.

Some cases refine existing M12 requirements; background-writer tests belong to the later consolidation work rather than an unbounded expansion of M12. Each needs a local implementation test before it can be reported as satisfied.

## Evaluation plan and unresolved work

A fair follow-up comparison should distinguish three tracks:

1. **Evidence retrieval:** identical source occurrences and query scope; measure eligible-source recall, complete-support coverage at a fixed rendered budget, exact-identifier reachability, and loss reasons. Report extraction bypassed versus live extraction separately.
2. **Context lifecycle:** long-running conversations, compaction, restart, source revision, and redaction during background work. Measure missing/duplicated source coverage and whether a model can reopen the cited evidence.
3. **Downstream agent tasks:** match the answer model, usable context, source visibility, and extraction tier; include task success, stale-claim use, abstention, latency, and model-call cost. A reflect agent cannot be compared directly with a bare search endpoint as though only retrieval changed.

Local multilingual parity must cover the same writing-system classes for all compared configurations. Dataset splits must remain independent of the examples used to tune extraction or packing. Provider-specific defaults and disabled channels must be reported, rather than silently replaced with stronger configurations.

Not completed: deploying these six systems, reproducing their published benchmarks, hosted-backend inspection, a full security/concurrency audit, source-scale latency measurements, or a matched oxibrain-versus-product evaluation. M12 remains a proposed implementation, and the acceptance additions above remain unimplemented. The completed result is a pinned, source-grounded architecture study with four limited function checks.
